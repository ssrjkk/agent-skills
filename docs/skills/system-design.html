System Design

Designing scalable, reliable systems.

Quick Start

1. Clarify requirements
2. Estimate scale
3. Sketch architecture
4. Design data model
5. Discuss trade-offs

When to Use

  • Designing new services or features
  • Scaling existing systems
  • Architecture reviews and interviews
  • Choosing between technologies

Best Practices

Requirements

  • Clarify functional and non-functional needs
  • Estimate users, QPS, data size, storage
  • Define latency and availability targets
  • State assumptions explicitly

Architecture

  • Start simple: services, DB, cache
  • Add components only when justified
  • Draw data flow end to end
  • Identify single points of failure

Data Model

  • Choose storage by access pattern
  • Plan for reads vs writes
  • Design for consistency needs
  • Consider partitioning and replication

Scaling

  • Scale vertically first, then horizontally
  • Add caching for hot reads
  • Use queues to decouple writes
  • Plan for failure domains

Dependencies

# whiteboard or diagramming tool

Examples

Requirements:
- 100M users, 10K QPS peak, 1KB avg request
- p99 latency < 200ms, 99.9% availability
- Reads 90% / writes 10%
Estimates:
- 10K QPS * 1KB = ~10 MB/s ingress
- 100M users * 100 bytes = ~10 GB user table
- 30 days retention => ~25 TB storage
Architecture:
[Client] -> [LB] -> [API services] -> [Cache] -> [DB]
                            \-> [Queue] -> [Workers]
Scaling options:
- Cache hot reads (Redis) for 90/10 read-heavy
- Shard user data by user_id
- Queue writes for async processing
- Replicate DB with a read replica

Step-by-Step

1. Clarify requirements and constraints.

2. Estimate scale (QPS, storage, retention).

3. Sketch a simple architecture.

4. Design the data model and storage.

5. Add caching, queues, and replication.

6. Identify bottlenecks and single points of failure.

7. Discuss trade-offs and alternatives.

8. Define monitoring and failure handling.

Validation

1. Architecture meets the QPS and latency targets

2. Storage estimates are covered

3. No single point of failure

4. Data consistency needs are met

5. Scaling path is clear

Troubleshooting

  • Over-engineering: add components only when needed.
  • Missed bottlenecks: trace the data flow and hot paths.
  • Unclear trade-offs: compare options with explicit criteria.

System Design (Системный дизайн)

Проектирование масштабируемых и надёжных систем.

Быстрый старт

1. Уточните требования
2. Оцените масштаб
3. Набросайте архитектуру
4. Спроектируйте модель данных
5. Обсудите компромиссы

Когда использовать

  • Дизайн новых сервисов или фич
  • Масштабирование существующих систем
  • Архитектурные ревью и интервью
  • Выбор между технологиями

Лучшие практики

Требования

  • Функциональные и нефункциональные
  • Оценка пользователей, QPS, объёма, хранения
  • Цели задержки и доступности
  • Явные допущения

Архитектура

  • Начните просто: сервисы, БД, кэш
  • Компоненты только когда обосновано
  • Поток данных end to end
  • Точки отказа

Модель данных

  • Хранилище под паттерн доступа
  • Планирование чтений vs записей
  • Консистентность
  • Партиционирование и репликация

Масштабирование

  • Сначала вертикально, затем горизонтально
  • Кэш для горячих чтений
  • Очереди для развязки записей
  • Домены отказа

Зависимости

# whiteboard или инструмент диаграмм

Примеры

Требования:
- 100M пользователей, 10K QPS пик, 1KB средний запрос
- p99 задержка < 200ms, доступность 99.9%
- Чтения 90% / записи 10%
Оценки:
- 10K QPS * 1KB = ~10 MB/s вход
- 100M пользователей * 100 байт = ~10 GB таблица
- retention 30 дней => ~25 TB хранилища
Архитектура:
[Client] -> [LB] -> [API services] -> [Cache] -> [DB]
                            \-> [Queue] -> [Workers]
Варианты масштабирования:
- Кэш горячих чтений (Redis) для 90/10 read-heavy
- Шардирование user data по user_id
- Очереди для async-обработки записей
- Реплика БД под чтения

Пошаговое руководство

1. Уточните требования и ограничения.

2. Оцените масштаб (QPS, хранилище, retention).

3. Набросайте простую архитектуру.

4. Спроектируйте модель данных и хранилище.

5. Добавьте кэш, очереди и репликацию.

6. Найдите бутылочные горлышки и точки отказа.

7. Обсудите компромиссы и альтернативы.

8. Определите мониторинг и обработку фейлов.

Валидация

1. Архитектура выдерживает QPS и задержку

2. Оценки хранения покрыты

3. Нет единой точки отказа

4. Потребности консистентности выполнены

5. Путь масштабирования ясен

Устранение неполадок

  • Пере-инжиниринг: компоненты только когда нужно.
  • Пропущенные бутылочные горлышки: трассируйте поток данных и горячие пути.
  • Неясные компромиссы: сравнивайте варианты по явным критериям.
