Code Review

Conducting thorough, actionable code reviews.

Quick Start

# Review a diff systematically
git diff main...HEAD
# check correctness, security, performance, and readability

When to Use

  • Every pull request before merge
  • Security-sensitive changes (auth, payments, data)
  • Refactors and large diffs
  • Onboarding and knowledge sharing

Best Practices

Prioritize

  • Review correctness and security first, style last
  • Separate blocking issues from nits
  • Focus on the diff, not the whole codebase
  • Read tests: do they cover the change?

Feedback Quality

  • Ask questions instead of demanding changes
  • Explain the "why" behind each suggestion
  • Suggest concrete fixes with examples
  • Acknowledge what is done well

Security & Performance

  • Look for injection, secrets, and unsafe deserialization
  • Check authz on every endpoint
  • Flag N+1 queries and O(n^2) patterns
  • Watch for unbounded inputs and resource leaks

Scope

  • Review the intent: does it solve the stated problem?
  • Check for dead code, leftovers, and debug output
  • Verify tests, docs, and migrations are included
  • Respect scope: propose follow-ups for large refactors

Dependencies

# Tools that help: ruff, mypy, eslint, golangci-lint
# Static security scanning: bandit, semgrep, gitleaks

Examples

# Risk: user-supplied value in SQL query
query = f"SELECT * FROM users WHERE id = {request.user_id}"  # SQL injection
# Fix: parameterize
cursor.execute("SELECT * FROM users WHERE id = %s", (request.user_id,))
# Risk: N+1 queries in a loop
for order in user.orders:           # 1 query per order
    items += order.items.all()
# Fix: eager load
from django.db.models import Prefetch
user.orders.prefetch_related(Prefetch("items"))
# Risk: missing authorization check
@app.route("/admin/users/<uid>")
def delete_user(uid):
    User.objects.get(id=uid).delete()   # no authz check
# Fix: verify the caller is an admin first
# Risk: secrets in code
API_KEY = "sk-live-abc123..."   # leaked secret
# Fix: use environment variables / secret manager

Step-by-Step

1. Read the PR description and understand the intent.

2. Scan the diff for obvious correctness and security issues.

3. Read tests; check they assert real behavior.

4. Review each file in order of risk (backend, auth, data).

5. Run static analysis if not already in CI.

6. Write feedback: blocking issues, questions, nits.

7. Approve only when blockers are resolved.

8. Follow up on deferred suggestions as issues.

Validation

1. No injection, broken authz, or leaked secrets

2. Tests cover the new behavior including edge cases

3. No N+1 queries or obvious performance regressions

4. Code matches project style and conventions

5. Every blocking comment addressed or justified

Troubleshooting

  • Large PR: request splitting or review by commits.
  • Missing tests: ask for tests on the changed paths.
  • Style bikeshedding: defer to the project linter/config.

Code Review (Ревью кода)

Проведение тщательных, практичных ревью кода.

Быстрый старт

# Систематически просмотрите diff
git diff main...HEAD
# проверьте корректность, безопасность, производительность и читаемость

Когда использовать

  • Каждый pull request до мержа
  • Security-sensitive изменения (auth, платежи, данные)
  • Рефакторинги и большие diff
  • Онбординг и обмен знаниями

Лучшие практики

Приоритеты

  • Сначала корректность и безопасность, стиль — в последнюю очередь
  • Отделяйте блокирующие проблемы от мелочей
  • Фокусируйтесь на diff, а не на всей кодовой базе
  • Читайте тесты: покрывают ли они изменение?

Качество фидбека

  • Задавайте вопросы вместо требования изменений
  • Объясняйте "почему" за каждой рекомендацией
  • Предлагайте конкретные исправления с примерами
  • Отмечайте, что сделано хорошо

Безопасность и производительность

  • Ищите injection, секреты и небезопасную десериализацию
  • Проверяйте authz на каждом эндпоинте
  • Отмечайте N+1 запросы и O(n^2) паттерны
  • Следите за неограниченными входами и утечками ресурсов

Объём

  • Оценивайте намерение: решает ли это заявленную проблему?
  • Проверяйте мёртвый код, остатки и debug-вывод
  • Убедитесь, что тесты, доки и миграции включены
  • Уважайте скоуп: для больших рефакторингов предлагайте follow-up

Зависимости

# Инструменты: ruff, mypy, eslint, golangci-lint
# Сканеры безопасности: bandit, semgrep, gitleaks

Примеры

# Риск: пользовательский ввод в SQL-запросе
query = f"SELECT * FROM users WHERE id = {request.user_id}"  # SQL injection
# Фикс: параметризация
cursor.execute("SELECT * FROM users WHERE id = %s", (request.user_id,))
# Риск: N+1 запросы в цикле
for order in user.orders:           # 1 запрос на заказ
    items += order.items.all()
# Фикс: eager load
from django.db.models import Prefetch
user.orders.prefetch_related(Prefetch("items"))
# Риск: отсутствие проверки авторизации
@app.route("/admin/users/<uid>")
def delete_user(uid):
    User.objects.get(id=uid).delete()   # нет проверки authz
# Фикс: сначала убедитесь, что вызывающий — админ
# Риск: секреты в коде
API_KEY = "sk-live-abc123..."   # утёкший секрет
# Фикс: используйте переменные окружения / secret manager

Пошаговое руководство

1. Прочитайте описание PR и поймите намерение.

2. Просмотрите diff на явные проблемы корректности и безопасности.

3. Читайте тесты; проверяйте, что они проверяют реальное поведение.

4. Ревьюйте файлы по порядку риска (backend, auth, данные).

5. Запустите статический анализ, если его нет в CI.

6. Напишите фидбек: блокирующие проблемы, вопросы, мелочи.

7. Аппрувьте только после решения блокеров.

8. Отложенные предложения выносите в issues.

Валидация

1. Нет injection, сломанной authz или утёкших секретов

2. Тесты покрывают новое поведение, включая edge cases

3. Нет N+1 запросов или явных регрессий производительности

4. Код соответствует стилю и конвенциям проекта

5. Каждый блокирующий комментарий решён или обоснован

Устранение неполадок

  • Большой PR: просите разбить или ревьюить по коммитам.
  • Нет тестов: просите тесты на изменённых путях.
  • Споры о стиле: отсылайте к линтеру/конфигу проекта.
