Карта 08: Вопросы и ответы с технических собеседований (DevOps / SRE)

Разбор реальных вопросов, на которых чаще всего срезаются кандидаты.

Блок 1: Linux и Сети

1. Что происходит под капотом, когда ты вводишь curl https://example.com?

  1. Парсинг URL и проверка кэша: curl выделяет схему (https), хост (example.com), порт (443).
  2. DNS-резолвинг: Системный вызов getaddrinfo проверяет /etc/nsswitch.conf -> читает /etc/hosts -> обращается к DNS-резолверу из /etc/resolv.conf (UDP/53) -> получает A/AAAA запись.
  3. TCP Handshake: Ядро открывает сокет и отправляет SYN пакет на IP:443 -> получает SYN-ACK -> отправляет ACK. Соединение переходит в статус ESTABLISHED.
  4. TLS Handshake (TLS 1.3): Клиент отправляет ClientHello (поддерживаемые cipher suites, SNI = example.com) -> Сервер отвечает ServerHello, присылает сертификат -> Клиент проверяет цепочку сертификатов через локальные Root CA (/etc/ssl/certs) -> вырабатываются симметричные сессионные ключи.
  5. HTTP-запрос: По зашифрованному каналу уходит GET / HTTP/2 с заголовком Host: example.com.
  6. Ответ и закрытие: Сервер возвращает HTTP-статус, заголовки и тело. После чтения данных соединение закрывается (FIN -> ACK).

2. На сервере df -h показывает 100% заполнение диска, а du -sh /* показывает, что занято всего 20%. В чем причина и как чинить?

  • Причина 1 (Самая частая): Удален большой лог-файл через rm, но процесс (например, Nginx или приложение) продолжает держать его файловый дескриптор открытым. Место на диске не освободится, пока процесс не закроет дескриптор.
  • Решение: Найти процесс через lsof | grep deleted (или lsof +L1), перезапустить/послать SIGHUP сервису или обнулить дескриптор на лету: truncate -s 0 /proc/<PID>/fd/<FD_NUM>.
  • Причина 2: Закончились inodes (проверяется через df -i) из-за миллионов мелких файлов (сессии, кэш).
  • Причина 3: Поверх непустой директории примонтировали другой раздел (файлы в старой директории скрыты точкой монтирования, но занимают место).

3. В чем разница между Load Average 10 на 4-ядерном сервере и CPU usage 100%?

  • В Linux в расчет Load Average входят не только процессы, которые прямо сейчас выполняются или ждут очереди на CPU (состояние R), но и процессы в состоянии Uninterruptible Sleep (D), которые ждут ответа от диска или сетевой шары (NFS).
  • Поэтому при поломке диска или зависании NFS Load Average может взлететь до 100+, при том что процессор будет простаивать (id ~ 95%, wa высокий).

4. Почему процесс в Docker-контейнере не завершается быстро по docker stop и убивается только через 10 секунд?

  • docker stop посылает сигнал SIGTERM процессу с PID 1 внутри контейнера, ждет 10 секунд (grace period) и посылает SIGKILL.
  • Потеря сигнала происходит по двум причинам:
  1. В Dockerfile использована shell-форма ENTRYPOINT " ./app " вместо exec-формы ENTRYPOINT ["./app"]. В shell-форме PID 1 получает /bin/sh -c, который не пробрасывает SIGTERM дочернему процессу.
  2. В ядре Linux процесс с PID 1 игнорирует сигналы по умолчанию, если в самом приложении явно не написан обработчик сигналов (signal handler). Решение — использовать ENTRYPOINT ["/sbin/tini", "--", "/app"] или флаг --init.

Блок 2: Kubernetes

5. Что происходит в кластере шаг за шагом, когда ты выполняешь kubectl apply -f deployment.yaml?

  1. kubectl валидирует манифест на клиенте и отправляет HTTP POST/PATCH запрос в kube-apiserver.
  2. kube-apiserver проводит аутентификацию, авторизацию (RBAC), прогоняет объект через Mutating Admission Webhooks (например, инжект сайдкара) и Validating Admission Webhooks (например, политики Kyverno), после чего сохраняет запись Deployment в etcd.
  3. Deployment Controller (внутри kube-controller-manager), подписанный на изменения через Watch API, видит новый Deployment и создает объект ReplicaSet в etcd.
  4. ReplicaSet Controller видит, что текущее число подов = 0, а желаемое = 3, и создает 3 объекта Pod в etcd (со статусом Pending, поле nodeName пустое).
  5. kube-scheduler видит неподвязанные поды, прогоняет алгоритмы фильтрации (Filtering: хватает ли requests, подходят ли taints/affinity) и оценки (Scoring), выбирает лучшую ноду и прописывает nodeName в спецификацию пода в etcd.
  6. kubelet на выбранной воркер-ноде видит, что на него назначен под, обращается через CRI к containerd: скачивает образ, вызывает CNI-плагин (Cilium/Calico) для создания сетевого namespace, veth-пары и выдачи IP-адреса, монтирует тома и запускает контейнеры через runc.
  7. После успешного прохождения readinessProbe контроллер EndpointSlices добавляет IP пода в список активных бэкендов Service.

6. В чем разница между livenessProbe и readinessProbe? Почему опасно проверять внешнюю БД в livenessProbe?

  • readinessProbe проверяет, готов ли под принимать входящий трафик. Если она падает — под не перезапускается, но его IP временно убирается из балансировки Service (Endpoints).
  • livenessProbe проверяет, не зависло ли приложение намертво (deadlock). Если она падает — kubelet убивает контейнер и запускает его заново.
  • Почему нельзя пинговать БД в livenessProbe: Если база данных кратковременно моргнет или замедлится под нагрузкой, у всех 50 реплик бэкенда одновременно упадет livenessProbe. Kubelet убьет все 50 подов одновременно, и при одновременном старте они положат базу лавиной новых подключений (Cascading Failure).

7. Что произойдет с подом при превышении requests и limits по CPU и Memory?

  • CPU — сжимаемый ресурс (compressible):
  • Превышение requests — ничего плохого, если на ноде есть свободные ядра.
  • Превышение limits — процесс не убивается, ядро Linux включает механизм CFS Quota и начинает троттлить (замедлять) контейнер, пропуская такты процессора (container_cpu_cfs_throttled_periods_total). Это приводит к росту задержек (Latency).
  • Memory — несжимаемый ресурс (incompressible):
  • Превышение requests — если на ноде начинается нехватка памяти (Node Memory Pressure), kubelet начнет выселять (Evict) поды, которые потребляют больше своего requests.
  • Превышение limits — мгновенно срабатывает cgroups OOM Killer, ядро посылает процессу SIGKILL (Exit Code 137), и под уходит в перезагрузку со статусом OOMKilled.

Блок 3: Terraform и CI/CD

8. Два инженера одновременно запустили terraform apply без блокировок. Что случится и как защититься?

  • Произойдет состояние гонки (Race Condition): оба процесса скачают старый terraform.tfstate, внесут разные изменения в облако, и тот, кто завершится вторым, перезапишет стейт поверх первого. Часть созданных ресурсов «потеряется» из стейта.
  • Защита: Использование Remote Backend с включенными блокировками (например, S3 backend с use_lockfile = true в современных версиях Terraform/OpenTofu или таблицей DynamoDB), а также вынос всех apply в единую очередь CI/CD (Atlantis / GitLab CI с resource_group).

9. Как заимпортить уже созданный руками ресурс в Terraform без простоя и пересоздания?

  1. Написать конфигурацию resource "aws_s3_bucket" "this" { ... } в .tf файле.
  2. Использовать декларативный блок import { to = aws_s3_bucket.this, id = "my-bucket-name" }.
  3. Запустить terraform plan и убедиться, что в плане 0 to destroy и нет изменений, требующих пересоздания (forces replacement).
  4. Применить terraform apply.
