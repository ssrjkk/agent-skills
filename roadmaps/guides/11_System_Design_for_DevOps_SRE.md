# Карта 11: Архитектура и System Design для DevOps / SRE собеседований

На позициях Middle+ и Senior часто дают задачу: *«Спроектируй инфраструктуру для высоконагруженного сервиса (10 000 RPS), которая переживет падение дата-центра и выдержит распродажу Черной Пятницы»*.

---

## 1. Путь трафика от пользователя до базы данных (Edge to Core)

1. **DNS и Глобальная маршрутизация:**
   - **GeoDNS / Anycast (Cloudflare, AWS Route53):** отдает IP ближайшего к пользователю пограничного узла (PoP) и проверяет Health Checks регионов.
2. **CDN и WAF (Edge Layer):**
   - Статика (`js`, `css`, картинки, видео) отдается напрямую с Edge-серверов CDN (Cache Hit Ratio > 95%), не доходя до наших серверов.
   - На уровне WAF режутся L7 DDoS-атаки, боты и SQLi/XSS-запросы.
3. **Внешняя балансировка (L4 -> L7):**
   - **L4 Load Balancer (NLB / IPVS / Cilium L4LB):** принимает TCP/UDP соединения и распределяет их по узлам L7-ингрессов.
   - **L7 Load Balancer / API Gateway (Envoy Gateway / Nginx / Kong):** терминирует TLS, проверяет JWT-токены, применяет Rate Limiting по IP/User-ID и маршрутизирует запросы в нужные микросервисы внутри Kubernetes.
4. **Вычислительный слой (Stateless Compute в K8s):**
   - Микросервисы развернуты минимум в **3 зонах доступности (Multi-AZ)** через `topologySpreadConstraints`.
   - Масштабирование подов через **HPA / KEDA** (по RPS или длине очереди), масштабирование нод через **Karpenter** (Spot + On-Demand).
5. **Слой кэширования и асинхронности:**
   - **Кэш чтения (Redis Cluster):** защищает БД от повторяющихся тяжелых SELECT-запросов (паттерн Cache-Aside).
   - **Очереди сообщений (Kafka / RabbitMQ):** сглаживают пики записи (Spikes). Например, при оформлении заказа API сразу кладет событие в Kafka и отвечает клиенту `202 Accepted`, а воркеры записывают заказы в БД со стабильной скоростью.
6. **Слой хранения данных (Stateful Storage):**
   - **PostgreSQL (CloudNativePG / Patroni):** 1 Primary (запись) + 2 Sync/Async Standby реплики в разных AZ (чтение) + пулер соединений **PgBouncer** перед ними.

## 2. Disaster Recovery (DR): RTO vs RPO

При проектировании бэкапов и мульти-региональности всегда отталкивайся от двух метрик бизнеса:
- **RPO (Recovery Point Objective):** *Сколько данных бизнес готов потерять в случае взрыва дата-центра?* (В единицах времени: например, RPO = 0 секунд означает синхронную репликацию между дата-центрами; RPO = 5 минут позволяет стримить WAL-архивы в S3 каждые 5 минут).
- **RTO (Recovery Time Objective):** *Как долго сервис может лежать, пока мы поднимаем резерв?* (Например, RTO = 2 минуты требует автоматического фейловера Patroni/Consul; RTO = 4 часа позволяет развернуть инфраструктуру с нуля через Terraform и накатить бэкап из S3).

| Стратегия DR | Описание | RTO | RPO | Стоимость |
| :--- | :--- | :--- | :--- | :--- |
| **Backup & Restore** | Бэкапы лежат в S3 другом регионе. При аварии поднимаем инфру через Terraform. | Часы | Минуты/Часы | $ (Минимальная) |
| **Pilot Light** | В резервном регионе уже крутится реплика БД, но вычислительные ноды выключены (скейлятся при аварии). | 10–20 минут | Секунды | $$ (Средняя) |
| **Warm Standby** | В резервном регионе работает уменьшенная копия всего стека. | 1–5 минут | Секунды | $$$ (Высокая) |
| **Multi-Region Active-Active** | Трафик обслуживается обоими регионами одновременно. | ~0 секунд | ~0 секунд | $$$$ (Максимальная) |
