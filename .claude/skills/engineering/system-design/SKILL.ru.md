# System Design (Системный дизайн)

> Проектирование масштабируемых и надёжных систем.

## Быстрый старт
```text
1. Уточните требования
2. Оцените масштаб
3. Набросайте архитектуру
4. Спроектируйте модель данных
5. Обсудите компромиссы
```

## Когда использовать
- Дизайн новых сервисов или фич
- Масштабирование существующих систем
- Архитектурные ревью и интервью
- Выбор между технологиями

## Лучшие практики

### Требования
- Функциональные и нефункциональные
- Оценка пользователей, QPS, объёма, хранения
- Цели задержки и доступности
- Явные допущения

### Архитектура
- Начните просто: сервисы, БД, кэш
- Компоненты только когда обосновано
- Поток данных end to end
- Точки отказа

### Модель данных
- Хранилище под паттерн доступа
- Планирование чтений vs записей
- Консистентность
- Партиционирование и репликация

### Масштабирование
- Сначала вертикально, затем горизонтально
- Кэш для горячих чтений
- Очереди для развязки записей
- Домены отказа

## Зависимости
```bash
# whiteboard или инструмент диаграмм
```

## Примеры
```text
Требования:
- 100M пользователей, 10K QPS пик, 1KB средний запрос
- p99 задержка < 200ms, доступность 99.9%
- Чтения 90% / записи 10%
```
```text
Оценки:
- 10K QPS * 1KB = ~10 MB/s вход
- 100M пользователей * 100 байт = ~10 GB таблица
- retention 30 дней => ~25 TB хранилища
```
```
Архитектура:
[Client] -> [LB] -> [API services] -> [Cache] -> [DB]
                            \-> [Queue] -> [Workers]
```
```text
Варианты масштабирования:
- Кэш горячих чтений (Redis) для 90/10 read-heavy
- Шардирование user data по user_id
- Очереди для async-обработки записей
- Реплика БД под чтения
```

## Пошаговое руководство
1. Уточните требования и ограничения.
2. Оцените масштаб (QPS, хранилище, retention).
3. Набросайте простую архитектуру.
4. Спроектируйте модель данных и хранилище.
5. Добавьте кэш, очереди и репликацию.
6. Найдите бутылочные горлышки и точки отказа.
7. Обсудите компромиссы и альтернативы.
8. Определите мониторинг и обработку фейлов.

## Валидация
1. Архитектура выдерживает QPS и задержку
2. Оценки хранения покрыты
3. Нет единой точки отказа
4. Потребности консистентности выполнены
5. Путь масштабирования ясен

## Устранение неполадок
- Пере-инжиниринг: компоненты только когда нужно.
- Пропущенные бутылочные горлышки: трассируйте поток данных и горячие пути.
- Неясные компромиссы: сравнивайте варианты по явным критериям.
